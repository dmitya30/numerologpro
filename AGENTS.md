## Назначение проекта

Проект переносит сайт `numerologpro.ru` с Ghost на полностью статический сайт из HTML, CSS, JavaScript и локальных статических ресурсов.

Production-сайт является продуктовой мультивизиткой «Тихого Дома». Он представляет отдельные продукты и предоставляет бесплатные точки входа в соответствующие Telegram-боты.

GitHub хранит исходный код и историю изменений. GitHub Pages используется для draft QA и production-публикации с пользовательским доменом `numerologpro.ru`.

## Правила команд и патчей

- Использовать только команды, совместимые с Git Bash.
- Никогда не использовать PowerShell и не предлагать PowerShell-синтаксис.
- Каждый исполняемый блок начинать с явного `cd` в требуемый каталог.
- Для локальных операций использовать канонический путь `~/projects/numerologpro`.
- Не предполагать текущую директорию.
- Не использовать `exit`, `exit 1` или другие команды, способные закрыть активную Git Bash или PuTTY-сессию.
- Не использовать `set -e`, `set -E`, `set -u` или `set -o pipefail` в командах, вставляемых в активную интерактивную оболочку.
- В интерактивных блоках безопасно отключать ранее включённый fail-fast через `set +e`, `set +u` и безопасную попытку `set +o pipefail`.
- Потенциально неуспешные проверки должны обрабатываться безопасно и не должны закрывать родительскую оболочку.
- Не оставлять незавершённые shell-конструкции, способные вызвать вторичное приглашение оболочки.
- Не использовать heredoc, включая `cat <<EOF` и Python heredoc.
- Один операционный шаг доставлять одним полным исполняемым блоком.
- Не разбивать одну операцию на несколько отдельно копируемых блоков.
- Использовать командные цепочки только тогда, когда следующий шаг не должен выполняться после неуспешной проверки.
- Не строить shell-логику так, чтобы после исключения или неуспешной проверки могло быть напечатано `PASS`.
- Не просить пользователя вручную исправлять код, сгенерированный ассистентом.
- Перед отправкой проверять синтаксис и quoting каждой команды.
- Изменённые отслеживаемые текстовые файлы должны заканчиваться ровно одним переводом строки без дополнительной пустой строки в конце.
- Перед сообщением `PASS` должен проходить `git diff --check`.


## Защита от ошибок генерации команд и скриптов

- Не передавать многострочные шаблоны или исходный код через несколько уровней shell- и Python-экранирования, если результат зависит от различия между `\n` и `\\n`.
- Для точечных преобразований существующих файлов предпочтительно использовать проверенные построчные anchors и `splitlines()`, а не большие многострочные строки внутри shell-команды.
- Все обязательные anchors, количество совпадений и итоговое содержимое должны быть проверены в памяти до первой записи изменяемых файлов на диск.
- Если escape-последовательности неизбежны, перед записью нужно отдельно проверить их фактическое значение или выполнить read-back проверку созданного временного результата.
- После исключения или ошибки патча необходимо проверить `git status`, staged diff и unstaged diff; нельзя предполагать, что файлы были изменены или не изменены.
- Запрет на heredoc действует также для исправляющих команд; успешное выполнение команды не отменяет нарушение этого правила.

## DNS cutover

DNS переключается только после того, как GitHub Pages preview прошёл технический и человеческий QA.

До DNS-изменений необходимо повторно проверить фактические записи домена у DNS-провайдера.

Нельзя полагаться только на ранее записанный DNS-аудит.

Перед cutover необходимо:

1. зафиксировать текущие DNS-записи;
2. подтвердить GitHub Pages custom domain;
3. проверить содержимое `CNAME`, если оно используется;
4. убедиться, что preview соответствует production-кандидату;
5. подготовить rollback-план;
6. проверить отсутствие несвязанных почтовых и сервисных записей, которые нельзя удалять;
7. только после этого изменить требуемые записи;
8. дождаться распространения DNS;
9. проверить apex и `www`;
10. проверить HTTPS;
11. проверить все обязательные маршруты и ресурсы;
12. сохранить Ghost и VPS до завершения согласованного периода наблюдения.

Нельзя отменять VPS сразу после первого успешного ответа GitHub Pages.

## Проверки

Использовать только реально существующие проектные проверки.

До появления проверочных скриптов нельзя придумывать их имена или утверждать, что они существуют.

При создании нового проверочного инструмента сначала обосновать необходимость и проверить отсутствие существующего аналога.

Минимальный набор проверок определяется после создания и инспекции фактической структуры репозитория.

Любой production-кандидат должен пройти:

- проверку синтаксиса используемых форматов;
- проверку внутренних ссылок;
- проверку локальных ресурсов;
- проверку удалённых Ghost-зависимостей;
- проверку SEO-метаданных;
- проверку sitemap и robots.txt;
- проверку коммерчески запрещённого контента;
- проверку `git diff --check`;
- draft deployment;
- человеческий визуальный QA.

## Формат файлов

- Не выполнять массовую замену окончаний строк без необходимости.
- Учитывать фактические правила `.gitattributes`, если файл существует.
- Не создавать `.gitattributes` без проверки необходимости.
- Не делать искусственные физические переносы строк внутри предложений, ссылок, строковых литералов, пользовательских текстов и model prompts.
- Каждый новый или изменённый текстовый файл должен завершаться ровно одним переводом строки.
- В production-контенте сохранять утверждённую типографику исходного языка.
- Не выполнять массовое переформатирование старого контента без отдельной задачи.

## Коммуникация и ответственность

- Не задавать лишние открытые вопросы, если ответ уже подтверждён документацией или фактическим состоянием.
- Если есть смысловая, архитектурная, юридическая или инфраструктурная развилка, сначала представить варианты и получить решение пользователя.
- Если информации достаточно для безопасного следующего шага, выполнить этот шаг без ожидания дополнительного приглашения.
- Если нужна информация пользователя, точно указать, чего не хватает и что именно заблокировано.
- Параллельно выполнять все неблокируемые задачи.
- Исправления пользователя имеют приоритет над прежними предположениями.
- После исправления обновлять источник истины и связанные документы, а не только подтверждать изменение в диалоге.
- Не объявлять миграцию завершённой до production QA на пользовательском домене.
